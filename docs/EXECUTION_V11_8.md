# v11.8 — خطة التراجع والنسخ الاحتياطي (تنفيذ Supabase PostgreSQL)

> حالة الوثيقة: مُجهزة ومُختبرة محلياً (اختبار الدخان 19/19 يشمل
> export/import). تُفعَّل خطوات الإنتاج بعد توفر `DATABASE_URL`.

## 1. نقاط الرجوع

| ما | أين | متى |
|---|---|---|
| وسم git `backup/pre-execution-3a8c52b` | محلي (يُرفع مع الفرع) | قبل أي تعديل — الإصدار المعتمد السابق |
| فرع التنفيذ `feat/supabase-pg-and-filter-fixes` | git | كل التغييرات معزولة عن main |
| main = `3a8c52b` | GitHub + نشر Render الحالي | الإصدار الجاري في الإنتاج |

التراجع الكودي = رفض الدمج أو `git revert` — **لا** يُمس main قبل اجتياز
الاختبارات، ودمج PR هو نقطة اللاعودة الوحيدة (autoDeploy).

## 2. النسخ الاحتياطي قبل الترحيل

1. تصدير البيانات الحرجة من الإنتاج (لوحة التحكم → تصدير، أو
   `scripts/migrate_sqlite_to_pg.py --from-dashboard <URL>`)
   — القائمة البيضاء: `app_settings, sources, rules, allowed_entities`
   (+ مرآة keywords عبر dashboard_store). يُحفظ JSON خارج Git.
2. تحقق قابلية القراءة: `python -c "import json;d=json.load(open(...));print({k:len(v) for k,v in d['tables'].items()})"`
3. نسخة المصدر تبقى محفوظة حتى انتهاء التحقق من الاستمرارية (المرحلة 8).

## 3. ترتيب التنفيذ الآمن (يمنع فقدان البيانات الجديدة)

```
[قاعدة Supabase فارغة]
  1. DATABASE_URL يُضاف في Render Dashboard (لا يُرسل في المحادثة)
  2. دمج PR → نشر جديد → الإقلاع ينشئ المخطط تلقائياً (DDL idempotent،
     مختبر double-start في الدخان)
  3. استيراد البيانات الحرجة: scripts/migrate_sqlite_to_pg.py
     --from-json backup.json (أو --from-dashboard)
  4. التحقق: عدادات src/dst لكل جدول (السكربت يفشل عند أي MISMATCH)
  5. RLS: scripts/supabase_rls.sql (مرة واحدة)
  6. إثبات الاستمرارية (المرحلة 8): إضافة إعداد → إعادة نشر → قراءته
```

## 4. التراجع بعد بدء استقبال بيانات الإنتاج

**قاعدة ذهبية:** حذف `DATABASE_URL` وحده ليس خطة تراجع — يعيد التطبيق إلى
SQLite **فارغة** بينما بيانات الإنتاج الجديدة كلها في Supabase.

سلم التراجع حسب السبب:

| السبب | الإجراء |
|---|---|
| خلل كودي بعد الدمج | `git revert` + إعادة نشر؛ **قاعدة البيانات تبقى Supabase** — الكود لا يعود لـ SQLite أبداً بعد الترحيل |
| خلل في Supabase نفسه (انقطاع طويل) | تصدير عاجل من PG (export_critical_data عبر لوحة/سكربت) + نشر إصدار سابق بـ SQLite مؤقت + استيراد JSON، مع تجميد الكتابة في الإصدار القديم قدر الإمكان |
| تلف بيانات جزئي | استعادة من آخر JSON احتياطي + مراجعة dead_letters |

بعد أي سيناريو يعيد SQLite مؤقتاً: عند عودة Supabase يُعاد التصدير→الاستيراد
بنفس السكربت (الاتجاهين مدعومان لأن export/import يعملان على المحركين).

## 5. ما لا يُفعل أبداً

- لا حذف/إعادة إنشاء جداول الإنتاج بأي أداة يدوية.
- لا `DROP` في Supabase SQL Editor قبل نسخة احتياطية موثقة.
- لا حذف متغيرات الحسابات (`*_SESSION_STRING`) بأي شكل — الجلسات خارج
  قاعدة البيانات تماماً (متغيرات بيئة) ولا تمر بالترحيل أصلاً.
