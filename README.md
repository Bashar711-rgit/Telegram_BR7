## 🆕 v10.6 — الوصول الأقصى لملف المرسل (كل مستخدم قابل للنقر — داخل حدود تيليجرام المشروعة)

1. **اكتشاف username عبر رسالة المصدر (S4 — الأقوى):** مرسل بلا username في الحدث/الكاش/DB يُحلّ الآن عبر `users.getUsers(InputUserFromMessage(peer, msg_id, user_id))` — آلية MTProto مشروعة: الحساب عضو في المجموعة المصدر وقد تسلّم رسالة المرسل بنفسه (نفس آلية فتح البروفايل من رسالة في العملاء الرسمية)، فتعمل حتى مع مستخدمين يخفيهم قائمة الأعضاء. الاسم المكتشَف يصبح رابط `t.me` عالمياً قابلاً للنقر، ويُحفَظ بCOALESCE (لا يلغي حقولاً موجودة) فيبقى كل تنبيه مستقبلي لهذا المرسل قابلاً للنقر، وaccess_hash الطازج يُخزَّن لكل حساب (يغذي mention tier-4). الكاش السلبي 5 دقائق + single-flight لكل مرسل + احترام FloodWait + مهلات محدودة + `NAV_USER_DISCOVERY_ENABLED` مفتاح إيقاف.
2. **تصلب المرساة الاحتياطية (hardening):** عندما يفشل سلّم mention (v10.4) بالكامل كان تيليجرام يحذف كيان `tg://user` صامتاً فيتحول الاسم لنص غير قابل للنقر — السبب الجذري لشكوى «مستخدم لا يُنقر». الآن مسار الإرسال الاحتياطي يستبدل المرساة برابط الرسالة المصدر المُتحقق منه: فتح الرسالة يتيح دائماً فتح ملف المرسل باللمس على صورته — **لكل مرسل أرسل رسالة، مهما كانت خصوصيته** (النص الظاهر متطابق بايت بايت).
3. **سلّم زر «مراسلة» الجديد:** `t.me/username` ← رابط الرسالة المصدر (HTTPS يعمل على كل العملاء) ← `tg://openmessage` (ديسكتوب فقط، آخر خيار بصدق). كل نقرة تصل لمكان حقيقي يقود لملف المرسل.
4. **حدود تيليجرام المعلنة بصدق (لا التفاف عليها):** مراسلة مستخدم منع خاصيته أو حظرنا لا يمكن فرضها (مفروضة من الخادم)؛ الحسابات المحذوفة لا روابط لها؛ المجموعات الأساسية بلا روابط رسائل — كلها تُعرض كما هي بدل روابط ميتة أو مُختلقة.

1. **تحذير التهيئة الجزئية:** عند تخطي حساب لغياب `_API_ID` مع وجود متغيرات أخرى له، يُسجل الآن تحذير صريح يعدّد المتغيرات الموجودة والمطلوبة بالضبط:
   ```
   Account MAIN SKIPPED: MAIN_API_ID is missing, but 2 other var(s) are set
   (MAIN_SESSION_STRING, MAIN_PHONE). Set MAIN_API_ID (and MAIN_API_HASH ...)
   ```
2. **تحذير فجوات الترقيم:** اكتشاف `ACCOUNT_1..20` يتوقف عند أول فجوة. إن وُجدت حسابات لاحقة مضبوطة (مثل ACCOUNT_3 بدون ACCOUNT_2) يُسجل تحذير بأن الترقيم يجب أن يكون متصلاً.

> 📌 **ملاحظة تشغيلية:** للتشغيل السحابي غير التفاعلي يلزم لكل حساب: `{prefix}_API_ID` + `{prefix}_API_HASH` + `{prefix}_PHONE` + `{prefix}_SESSION_NAME` (+ `{prefix}_SESSION_STRING` لتسجيل الدخول دون تفاعل). أي متغير ناقص سيظهر تحذيره في السجل عند الإقلاع مباشرة.

أسفل كل رسالة تنبيه في القناة الهدف صفّان من الأزرار:

| **تواصل مع المرسل** | Inline | يعرض قائمة الرسائل الجاهزة كاملة — يختار المشرف واحدة فتُرسل فوراً إلى صاحب الطلب |

**الرسائل الجاهزة** (قابلة للتعديل عبر `CONTACT_TEMPLATES_JSON`) — 5 قوالب مدمجة (بحث / CV / واجبات × 2 / مشروع).

**مسار احتياطي** (يعمل دائماً حتى لو لم تصل أحداث الأزرار التفاعلية): رد على التنبيه بكلمة **«تواصل»** لإظهار القائمة، أو رد برقم **1-5** لإرسال الرسالة المختارة.

### المرحلة الثانية — نظام مكافحة المعلنين والسبام

```
Watch List (مراقبة 10 دقائق — لا حظر ولا تجاهل)
   │  شرط 1: رسالتان خلال 60 ثانية (أي مجموعات)
   │  شرط 2: رسائل متشابهة ≥ 80% خلال 5 دقائق
   │  شرط 3: أكثر من طلب من فئات مختلفة خلال 5 دقائق
   ▼
Spam Confirmation (أي شرط أثناء المراقبة)
   │  طلب جديد/معاد صياغته، رسالة إضافية خلال 5 دق،
   │  الانتقال لمجموعات أخرى بنفس الغرض، فئات متعددة،
   │  5 رسائل/10 دق أو 3 مجموعات/10 دق
   ▼
Permanent Ignore (Cross-Group Spam / Mass Poster)
      إيقاف كل التنبيهات + تجاهل كل الرسائل المستقبلية
      + تسجيل سبب الحظر بالتفصيل + ينجو من إعادة التشغيل

تصنيف مباشر (دون مراقبة): نفس الرسالة/المعنى في 4 مجموعات خلال 5 دقائق
```

- كل العتبات قابلة للتعديل الحي من لوحة التحكم (مجموعة «مكافحة السبام»).
- أوامر المشرف: `/spam` (تقرير القوائم) و `/unspam <id>` (إزالة من التجاهل) و `/contact` (عرض الرسائل الجاهزة).
- المستخدم تحت المراقبة يستمر في تلقي التنبيهات كالمعتاد — التأكيد فقط يوقفها.

### المرحلة الثالثة — إصلاح قاعدة البيانات (int32 overflow)

- `alert_dedup.sender_id` كان يبقى `INTEGER` (int4) في PostgreSQL → الآن `BIGINT`.
- ترحيل BIGINT شامل لكل أعمدة المعرفات (14 عموداً في 9 جداول) مع إعادة محاولة عند فشل الأقفال.
- فشل الترحيل لم يعد يُبتلع بصمت: سجل ERROR + تحقق فعلي من `information_schema` بعد الترحيل وتحذير CRITICAL عند أي عمود متبقٍ int4.
- جداول جديدة: `spam_watch` + `spam_ignore` (معرفات BIGINT من اليوم الأول).

## ☁️ النشر على Render (الطريقة المعتمدة)

1. ارفع المشروع إلى GitHub (بدون `accounts.env` — محمي بـ `.gitignore`).
2. أنشئ **Web Service** جديداً (plan: free) واربطه بالمستودع:
   - Build Command: `pip install -r requirements.txt`
   - Start Command: `python main.py`
   - Health Check Path: `/health`
3. أضف متغيرات البيئة من لوحة Render > Environment (انظر الجدول أدناه).
4. بعد تشغيل الخدمة افتح `https://<service>.onrender.com/login` وسجّل كل حساب برمز OTP — تُحفظ الجلسة تلقائياً ويُعاد النشر.
5. (موصى به) اربط [UptimeRobot](https://uptimerobot.com) بـ `/health` كل 5 دقائق لضمان عدم السبات.

> **ملاحظة:** قاعدة SQLite على الخطة المجانية مؤقتة (تُصفَّر عند إعادة النشر). للاستمرارية أنشئ PostgreSQL وأضف `DATABASE_URL`.
